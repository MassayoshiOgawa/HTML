FAULT 1 -- ReplaceSlotStampsCommand aspect ratio corruption
----------------------------------------------------------------------
Location: editor.html, _applyConfig() method
Severity: HIGH
Description: The width was calculated AFTER overwriting stamp.height with
  the new value. The expression:
    stamp.width = stamp.width > 0 && stamp.height > 0
      ? Math.round(stamp.width * (newHeight / stamp.height))
      : newHeight;
  divided by the ALREADY-UPDATED stamp.height (= newHeight), making the
  ratio newHeight/newHeight = 1, so stamp.width never changed. All replaced
  stamps kept their original width regardless of the new height, causing
  aspect ratio distortion.
Correction: Saved the old height before overwriting:
    const oldHeight = stamp.height;
    stamp.height = newHeight;
    stamp.width = oldHeight > 0
      ? Math.round(stamp.width * (newHeight / oldHeight))
      : newHeight;
Tests re-executed: Replace Existing Stamps / Undo / Redo -- all PASS

FAULT 2 -- Native confirm() used instead of custom modal dialog
----------------------------------------------------------------------
Location: editor.html, _checkSlotReplaceConfirmation() at line 1613
Severity: MEDIUM
Description: Used browser-native confirm() which is blocking, inconsistent
  with app's custom confirmAsync() modal. The native dialog could not be
  styled and offered inconsistent UX.
Correction: Replaced confirm() with await app.confirmAsync() and made the
  method async. Updated all 6 call sites (image upload, size, appear effect,
  disappear effect, image effect, wobble) to use await.
Tests re-executed: Replace Existing Stamps / Cancel confirmation -- all PASS

FAULT 3 -- Fading pen (FadingPenTool) had no Undo/Redo support
----------------------------------------------------------------------
Location: editor.html, FadingPenTool.onMouseUp()
Severity: MEDIUM
Description: Fading strokes were pushed directly to
  EditorState.tools.fadingStrokes without adding entries to the history
  stack. Undo/Redo had no effect on fading strokes.
Correction:
  1. Added _fsIdCounter and _hiddenFsIds to EditorState.tools for tracking.
  2. Modified FadingPenTool.onMouseUp() to assign a unique _fsId to each
     stroke and push a { _type: 'fading-stroke', _fsId } entry to the
     undoStack.
  3. Extended historyManager.undo() and redo() to handle the 'fading-stroke'
     type by adding/removing the fsId from _hiddenFsIds.
  4. Modified _renderFadingCanvas() to skip strokes in _hiddenFsIds.
  5. Cleared _hiddenFsIds when loading a new image.
Tests re-executed: Fading Pen / Undo / Redo -- all PASS

3. KNOWN LIMITATIONS AND UNRESOLVED ISSUES
================================================================================

LIMITATION 1 -- Continuous stamp effects (Blink, Wobble) only in preview
----------------------------------------------------------------------
Description: The blink and wobble effects are correctly implemented in the
  StampPreviewManager and display during the stamp preview (while holding
  the slot key). However, once a stamp is placed, these continuous effects
  are not applied to the placed DOM elements. The stamp data stores the
  imageEffect and imageEffectSettings fields, but no runtime loop applies
  CSS transforms/opacity changes to placed stamps.
Impact: Users can configure blink/wobble for slots, see the effect during
  preview, but placed stamps appear static.
Severity: Medium -- This is a missing feature rather than a regression.
Workaround: None currently. A StampEffectRuntime class would need to track
  placed stamps with continuous effects and run animation loops.

LIMITATION 2 -- No loading/progress indicator for image file reads
----------------------------------------------------------------------
Description: When loading large images (main background or slot uploads),
  there is no progress indicator. The UI freezes briefly during
  FileReader.readAsDataURL() or URL.createObjectURL() for large files.
Impact: Users may think the application is unresponsive when loading large
  images (>10MB).
Severity: Low

LIMITATION 3 -- localStorage size limit (approx 5-10MB per origin)
----------------------------------------------------------------------
Description: Both autosave and stamp slot settings use localStorage. The
  autosave stores the full background image as a data URL, which can be
  very large for high-resolution images. A 4MB guard is in place, but
  once reached, autosave silently stops working. No fallback to IndexedDB
  is implemented.
Impact: Autosave may silently fail for projects with large background
  images, especially when combined with many stamps.
Severity: Low (graceful degradation, warning shown)

LIMITATION 4 -- Stamp rendering uses individual DOM elements
----------------------------------------------------------------------
Description: Each stamp is a separate <img> element. With 1000+ stamps,
  DOM operations (renderAll, clear, syncAllElements) may be slow.
Impact: Performance degrades with very large stamp counts.
Severity: Low for typical usage (<100 stamps). Medium for extreme cases.

LIMITATION 5 -- Fading stroke undo/redo not persisted across sessions
----------------------------------------------------------------------
Description: Hidden (undone) fading stroke IDs (_hiddenFsIds) are not
  serialized in the project export or autosave. On restore, all fading
  stroke entries are re-added to the undo stack without the hidden flag.
  Since fading strokes auto-expire, this is rarely noticeable.
Impact: Undone fading strokes may re-appear briefly after session restore
  if their lifetime has not expired.
Severity: Low
