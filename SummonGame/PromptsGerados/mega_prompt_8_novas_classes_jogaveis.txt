VISAO GERAL DA ARQUITETURA ATUAL (para consulta rapida)
================================================================================

- Jogo top-down 2D em HTML5 Canvas, single-file.
- Classe Game centraliza tudo: entidades, loop, renderizacao.
- PlayerClasses: objeto com definicoes das classes jogaveis.
  Atualmente: { none, oracle, scout }.
  Cada classe tem: name, desc, abilityName, cooldown, duration, icon.
- ActivateAbility: chamado via tecla F (keybinds.ability).
  Verifica cooldown > 0 ou abilityActive.
  Se ok: abilityActive = true, abilityTimer = duration, abilityCooldown = cooldown + duration.
- Player tem: baseSpeed (140), speed (calculado por frame),
  abilityCooldown, abilityActive, abilityTimer, playerClass, playerIndex.
- Sistema de Habilidade: #ability-hud mostra nome, barra de cooldown,
  timer numerico, status (Active/CD/Ready).
- Sistema de interacao: hold-to-activate com checkInteraction().
- Sistema de traps: Game.traps[] com posicao, stun, trapColor, trapRadius.
- Sistema de shop: Game.shopItems[] com itemKey, price, sold.
- Sistema de monstro: FSM patrol/chase/search com pathfinding BFS.
- Sistema de visao: raycasting poligonal com isPointVisible().
- Sistema de particulas: Particle[] para efeitos visuais.
- Sistema de multiplayer: ate 4 jogadores, cada um com seus proprios
  atributos e keybinds.

CLASSE 1: Red Hacker
================================================================================

PlayerClasses key: 'redhacker'

name: 'Red Hacker'
desc: 'Cria um clone seu que persegue e stuna o monstro por 3s'
abilityName: 'Clone Perseguidor'
cooldown: 20
duration: 0 (instantaneo, nao tem duracao de habilidade ativa - o clone que tem duracao)
icon: 'R' (ou 'RH', algo representativo)

COMPORTAMENTO:
- Ao ativar a habilidade (tecla F):
  * Cria um clone na posicao atual do jogador.
  * O clone sabe EXATAMENTE onde o monstro esta (ignora fog/visao).
  * O clone persegue o monstro usando pathfinding BFS (reutilizar Game.findPath)
    ate o tile do monstro, recalculando a cada frame.
  * Se o clone tocar no monstro (distancia < TILE_SIZE * 0.8, mesma logica de ataque):
    - Monstro fica stunado por 3 segundos (monster.stunTimer = 3).
    - Clone desaparece (explode em particulas ou simplesmente some).
  * Se o clone nao tocar no monstro em ate 8 segundos, ele desaparece.
  * So pode haver 1 clone ativo por Red Hacker por vez.
  * Cooldown comeca APOS o clone desaparecer (seja por toque ou timeout).

APARENCIA DO CLONE:
- Renderizado como o proprio jogador (circulo colorido com olhos e nome),
  mas com globalAlpha = 0.3 (30% de opacidade).
- Nao tem nome renderizado acima.
- Deve ter um indicador sutil (ex: borda pontilhada) para distinguir.

COMPORTAMENTO FISICO:
- O clone nao colide com o jogador.
- O clone nao pode passar por paredes (usa pathfinding BFS normal).
- O clone nao causa dano - apenas stuna ao tocar.
- O clone ignora portas (pode atravessa-las independente do estado).
  DICA: em canMoveTo do clone, tratar tile 'd' como sempre passavel.
- O clone nao pode ser atacado/danificado.

IMPLEMENTACAO SUGERIDA:
- Adicionar uma estrutura para rastrear clones: Game.activeClones[] ou
  um array de objetos { playerIndex, px, py, alive, timer, targetMonster }.
- No Game.update(), atualizar clones (movimento, colisao com monstro, timer).
- No Game.render(), renderizar clones antes dos monstros, com alpha 0.3.
- No activateAbility, se playerClass === 'redhacker', criar clone.
- O cooldown so deve comecar a contar quando o clone morrer/desaparecer.
  Para isso: abilityCooldown so e definido quando clone expira/toca.
  Enquanto clone estiver vivo, NÃO iniciar cooldown.

COMPORTAMENTO:

- CARACTERISTICAS DA PAREDE:
  * Tamanho: 3 tiles de comprimento.
  * Largura: 25% do TILE_SIZE (8 pixels).

  * A parede NAO bloqueia visao do jogador (raycasting do jogador ignora).
  * A parede NAO bloqueia pathfinding BFS do jogador.
  * A parede BLOQUEIA pathfinding BFS do monstro (trata como obstaculo).

    nos ultimos ~200ms antes da ativacao:
    -> Parede vertical (3 tiles empilhados na vertical, norte-sul)
    EXEMPLO: tiles em (playerX, playerY-1), (playerX, playerY), (playerX, playerY+1)
  * Se o jogador estava se movendo verticalmente (dy != 0, |dy| > |dx|):
    -> Parede horizontal (3 tiles na horizontal, leste-oeste)
    EXEMPLO: tiles em (playerX-1, playerY), (playerX, playerY), (playerX+1, playerY)
  * Se o jogador estava parado (dx=0, dy=0):
    -> Parede horizontal (padrao).
  * Diagonal: considerar o eixo com maior magnitude absoluta.

- A parede e centrada no tile do jogador no momento da ativacao.

IMPLEMENTACAO SUGERIDA:

  onde orientation = 'horizontal' | 'vertical'.

- Em Game.update(): decrementar timer, quando <= 0 remover.
- Em Game.render(): desenhar a parede (retangulo semi-transparente).

- Em Game.findPath(): BLOQUEAR tiles que contem a parede para o monstro.
- Em MonsterEntity.hasLineOfSight(): BLOQUEAR linha de visao pela parede.
- Para o monstro nao ver atraves: monster.hasLineOfSight() deve verificar
  se ha uma parede entre origem e destino.
- Simbolo: usar um tile virtual. A parede nao e um tile no mapa, e sim
  uma entidade separada que afeta colisao/pathfinding do monstro.

DETALHES DE COLISAO:
- A parede ocupa uma area retangular. Para colisao com o monstro:
  - Se orientation === 'horizontal':
    - Ocupa os tiles (tileX-1, tileY), (tileX, tileY), (tileX+1, tileY).
    - Na pratica: cada tile tem uma "faixa" no meio que bloqueia.
    - O monstro canMoveTo deve retornar false se o monstro estiver
      tentando entrar em qualquer desses 3 tiles.
  - Similar para vertical: (tileX, tileY-1), (tileX, tileY), (tileX, tileY+1).

PARA SIMPLIFICAR:

  como 'O' (wall).
- Para a linha de visao do monstro, tiles ocupados pela parede bloqueiam.
- Para colisao do monstro, tiles ocupados bloqueiam.
