REQUISITO 1 - ALTAR 2x2 (4 TILES EM QUADRADO)
================================================================================

PROBLEMA: Atualmente o jogo so reconhece UM tile 'A' como altar (game.altarPos armazena apenas o ultimo encontrado). Nao ha suporte para 4 tiles 'A' em formato 2x2 agindo como um unico altar maior.

SOLUCAO: Implementar sistema de deteccao de altar 2x2, similar ao sistema de agrupamento de portas (double door). Quando 4 tiles 'A' formarem um quadrado 2x2, o jogo deve trata-los como UM unico altar.

MUDANCAS NO CODIGO:

a) Game - NOVAS PROPRIEDADES:
   altarGroups: array de objetos { minX, minY, maxX, maxY, centerX, centerY } - grupos de 2x2 detectados
   altarSingles: array de {x, y} - tiles 'A' isolados (nao parte de grupo 2x2)
   Substituir o uso de game.altarPos (unico) por deteccao de grupos + singles.

b) parseMap() - MODIFICAR:
   Coletar TODAS as posicoes de 'A' em um array (ex: altarPositions[]), nao apenas a ultima.
   Remover a propriedade altarPos do retorno.

c) Game.loadMap() - NOVA LOGICA (apos criar doorEntities):
   Receber todas as posicoes de 'A' do mapData.
   Detectar grupos 2x2:
     Para cada posicao 'A' (x, y), verificar se (x+1, y), (x, y+1), (x+1, y+1) tambem sao 'A'.
     Se sim: e um grupo 2x2. Calcular:
       minX = x, minY = y (canto superior esquerdo)
       maxX = x+1, maxY = y+1 (canto inferior direito)
       centerX = (minX + maxX + 1) / 2 * TILE_SIZE (centro em pixels entre os 4 tiles)
       centerY = (minY + maxY + 1) / 2 * TILE_SIZE
     Armazenar em altarGroups[].
     Remover as 4 posicoes do pool de singles.
   Para as posicoes 'A' restantes (nao agrupadas): adicionar em altarSingles[].

d) Player.checkInteraction() - MODIFICAR:
   Verificar distancia para CADA altar (grupo ou single):
     - Para grupos: usar centerX/centerY como posicao de referencia
     - Para singles: usar (x+0.5)*TILE_SIZE, (y+0.5)*TILE_SIZE
   Escolher o mais proximo dentro do raio de interacao (1.5 tiles).
   Armazenar em p.interactTarget se for altar: { type: 'altar', isGroup: bool, groupData, x, y }

e) Game.renderInteractionCircle() - MODIFICAR:
   Se o alvo for um altar EM GRUPO, desenhar o circulo de progresso no CENTRO do grupo (centerX, centerY).
   Se for altar single, manter comportamento atual (desenhar no tile do altar).

f) Game.renderTiles() - MODIFICAR (case 'A'):
   Se o tile 'A' faz parte de um grupo 2x2, renderizar os 4 tiles como uma unica area de altar (cor vermelha #ff4444 em todos os 4, talvez com um glow central unificado).
   Se for altar single, manter renderizacao atual.

g) Game - altarPos removido:
   Substituir todas as referencias a game.altarPos pelo novo sistema de altarGroups + altarSingles.

h) Game.findPath() - BFS:
   Tile 'A' continua passavel (como antes). Nao requer alteracao.

i) Altar interaction:
   Quando o player interage com um grupo 2x2, o comportamento e identico a um altar single (hold E por 2s para invocar). Apenas a posicao da barra de progresso e o centro visual mudam.

REQUISITO 4 - MONSTER FIXES
================================================================================

PROBLEMA 4A - JESTER NAO ANDA SOBRE TRAPS:
Atualmente o Jester, ao buscar traps (trapSeeking), para quando chega PERTO da trap em vez de andar sobre ela.
No updateJester(), a logica de deteccao de trap (nearestDist < TILE_SIZE * 0.5) so funciona se o Jester estiver muito perto, mas ele para de se mover antes de alcancar a trap porque o pathfinding BFS evita tiles com traps ou a colisao/caminhada falha.

SOLUCAO 4A:
No updateJester(), o monstro deve caminhar ATE em cima da trap (dist < TILE_SIZE * 0.2) em vez de parar a 0.5 tile.
Ajustar o threshold de chegada na trap: mudar de TILE_SIZE * 0.5 para TILE_SIZE * 0.2.
Verificar se o pathfinding/BFS esta bloqueando o tile da trap. Se estiver, o Jester deve poder andar sobre traps (ignorar traps no pathfinding).
No followPath, o Jester em modo trapSeeking nao deve ser bloqueado por traps.
O Jester ainda ativa a trap ao chegar nela (stun e remocao).

PROBLEMA 4B - ALIEN GRANDE APENAS EM PATROL:
Atualmente Alien so e grande quando nao esta transformado (!isTransformed). O isTransformed fica true quando detecta player. O usuario quer que:
- Em PATROL: Alien pequeno (radius * 0.5) - comportamento atual
- Em CHASE: Alien GRANDE (radius normal, isTransformed = true)
- Em SEARCH: Alien GRANDE (radius normal, isTransformed = true)

SOLUCAO 4B:
Modificar a logica de transformacao do Alien:
- isTransformed = (this.state === 'chase' || this.state === 'search')
- Ou seja, o Alien so e pequeno em patrol. Em chase e search, ele fica grande.
- Remover a deteccao do player como gatilho de transformacao.
- A velocidade do Alien:
  Patrol: speed = baseSpd / 3 (lento, pequeno)
  Chase: speed = baseSpd * (4/3) (rapido, grande, ativo)
  Search: speed = baseSpd (normal, grande mas nao em perseguicao ativa)

MUDANCAS:
No update() do monstro, bloco if (this.type === 'alien'):
  Mudar de:
    const detected = this.canSeePlayer() || this.canDetectBehind();
    this.isTransformed = detected;
  Para:
    this.isTransformed = (this.state === 'chase' || this.state === 'search');

No render() do monstro:
  if (this.type === 'alien' && !this.isTransformed) radius = baseRadius * 0.5;
  Isso permanece igual, mas agora isTransformed reflete o estado, nao a deteccao.

PROBLEMA 4C - RUSH NAO FICA MAIS RAPIDO COM HABILIDADES:
Atualmente notifyRushMonsters() adiciona 20 a rushSpeedBonus e ao speed do monstro. Porem, no update() do monstro, o speed e recalculado DO ZERO todo frame: this.speed = (mt.speedMod || 1) * this.game.getMonsterSpeed(). Isso sobrescreve o bonus adicionado por notifyRushMonsters, fazendo com que Rush nunca fique mais rapido.

SOLUCAO 4C:
No update() do monstro, apos calcular this.speed, adicionar this.rushSpeedBonus:
  this.speed = (mt.speedMod || 1) * this.game.getMonsterSpeed() + this.rushSpeedBonus;
Isso garante que o bonus acumulado seja aplicado e mantido.

PROBLEMA 4D - RAT KING: RATOS COMEM TRAPS 65% MAIS RAPIDO:
Atualmente ratos do Rat King tem devourTimer = 35 (segundos para comer uma trap). O usuario quer 65% mais rapido.

SOLUCAO 4D:
No updateRatEntities(), na linha onde rato comeca a devorar:
  Mudar de: rato.devourTimer = 35;
  Para: rato.devourTimer = 35 * (1 - 0.65) = 35 * 0.35 = 12.25;
  Ou seja: rato.devourTimer = 35 * 0.35;
