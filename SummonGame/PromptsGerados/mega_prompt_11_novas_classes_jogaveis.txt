VISAO GERAL DA ARQUITETURA ATUAL (para consulta rapida)
================================================================================

- Jogo top-down 2D em HTML5 Canvas, single-file (~5139 linhas).
- Constantes principais: TILE_SIZE = 32, PLAYER_COUNT (ate 4).
- Game centraliza tudo: entidades, loop, renderizacao.
- PlayerClasses: objeto com definicoes das classes jogaveis.
  Atualmente contem: oracle, scout, redhacker, commandyeller, boringtrapper,
  dyingguy, teevee, annoyinglooper, timetraveler, luckyspender (10 classes).
  Cada classe tem: name, desc, abilityName, cooldown, duration, icon.
  NOTA: cooldown=0 e duration=0 indica habilidade passiva (tecla F ignorada).
- activateAbility(game, player): chamada ao pressionar tecla F (keybinds.ability).
  Verifica cooldown>0 ou abilityActive. Se ok, executa logica da classe.
  Atualmente trata com switch: timetraveler, redhacker, scout, commandyeller,
  dyingguy, annoyinglooper (os outros usam o fluxo padrao: abilityActive=true,
  abilityCooldown=cooldown+duration).
- Player: construtor recebe tileX, tileY, playerIndex, name, playerClass.
  Propriedades: px, py, speed, baseSpeed (140), hp (100), maxHp (100), alive,
  interacting, interactTimer, interactTarget, interactType, invulnTimer,
  playerClass, abilityCooldown, abilityActive, abilityTimer,
  keybinds, inventory[5], selectedSlot, useTimer, using, useTapPending,
  speedItemTimer, speedItemMult, commandYellMult, commandYellTimer,
  invisible, invisibleTimer, timeTravelUsed, duplicatedSlots (Set),
  lastDx, lastDy.
- Player.update(dt, game): atualiza cooldowns, buffs timers, calcula speed
  (baseSpeed + scout 1.5x + speedItemMult + commandYellMult), move,
  checkInteraction, gerencia hotbar tap/hold.
- Player.checkInteraction(game): verifica entidades proximas (portas, altar,
  artefatos, shops, lixeiras). Define interactTarget e interactType.
  Alvos: 'door', 'altar', 'artifact', 'shop', 'trash'.
- Interacao: hold E para interagir (portas sao toggle instantaneo). Duracao:
  door=0.3s, altar=4s, artifact=1.5s + 2.5*(playerCount-1).
- Hotbar: tecla R. Tap (<0.3s) cicla entre slots ocupados. Hold (>=1s)
  usa item equipado (chama game.useItem). Circular progress bar no hold.
- Game.useItem(player): traps (cria trap), consumables (aplica efeito).
- Game.buyFromShop(player, shopData): compra item, logica do Lucky Spender.
- Game.sellItem(player): vende item equipado, bloqueia duplicated do Lucky
  Spender.
- DoorEntity: toggle(), open, animating, solid (getter: !open && !animating),
  groupMembers. Portas sao animadas (abertura/fechamento).
- MonsterEntity: FSM (patrol/chase/search), BFS pathfinding (Game.findPath),
  stunTimer, speed (varia por tipo), canSeePlayer, canDetectBehind.
- Game.traps[]: objetos com x, y, item, active, stun, trapColor, trapRadius,
  tauntDuration, tauntTimer, tauntedMonster.
- Game.activeClones[]: array de clones do Red Hacker.
- Game.activeWalls[]: array de paredes do Annoying Looper.
- Game.activeMonsters[]: monstros ativos no round.
- Game.artifactEntities[]: artefatos no mapa.
- Game.shopItems[]: lojas com itemKey, price, sold.
- Game.currency: moeda compartilhada entre jogadores.
- Game.playerCount: numero de jogadores.
- Game.playerClasses[]: array de strings com classe de cada jogador.
- Game.playerNames[]: array de strings com nome de cada jogador.
- Fim de round: Game.checkGameState() verifica se todos artefatos foram
  coletados e todos monstros estao mortos. Chama loadMap() para novo round.
- Fog of war: raycasting poligonal com isPointVisible().
- HUD: paineis HTML (#hud, #ability-hud, #hotbar-container, etc).

================================================================================
SISTEMA DE MINI-MENU REUTILIZAVEL (ARQUITETURA FUTURA)
================================================================================

Para escalabilidade, o sistema de mini-menu deve ser projetado como um
componente reutilizavel. Abaixo esta a arquitetura sugerida para
implementacao futura (apos o Helpful Priest funcionar com a versao
hardcoded inicial).

ESTRUTURA GENERICA:
{
  owner: Player,           // quem abriu o menu
  targets: Array,          // array de alvos (players, artefatos, etc)
  selectedIndex: number,   // indice selecionado
  open: boolean,           // menu aberto?
  useTimer: number,        // timer de hold
  useTapPending: boolean,  // flag de tap
  holdDuration: number,    // duracao do hold para ativar (default 1.0)
  tapDuration: number,     // duracao maxima do tap (default 0.3)
  onActivate: function(target, owner, game),  // callback ao completar hold
  renderSlot: function(ctx, x, y, target, index, isSelected, game), // custom render
  getSlotCount: function(targets), // quantos slots renderizar
  positionOffset: { dx: number, dy: number }  // offset relativo ao owner
}

FUNCOES DO SISTEMA:
- createMiniMenu(owner, targets, options): cria e retorna objeto mini-menu.
- updateMiniMenu(menu, dt, keys, keybind): atualiza logica tap/hold.
- renderMiniMenu(ctx, menu, game): renderiza o menu.
- closeMiniMenu(menu): fecha e limpa.

Desta forma, futuras classes podem criar mini-menus com:
- Targets diferentes (ex: lista de waypoints para teleporte, lista de
  artefatos para visao remota).
- Acoes diferentes (ex: buffar, teleportar, marcar).
- Visuais customizados (ex: icones de artefatos em vez de jogadores).

Nota: Esta arquitetura NAO precisa ser implementada completamente agora.
Implemente primeiro a versao hardcoded do Helpful Priest. A estrutura
generica pode ser refatorada depois, quando outra classe precisar de
mini-menu. O importante e que o codigo do Helpful Priest seja escrito
com funcoes separadas e parametros claros, facilitando a extracao futura.
