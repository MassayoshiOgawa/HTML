1. VISAO GERAL DA ARQUITETURA
================================================================================

Summon Game e um jogo top-down 2D em tempo real renderizado em HTML5 Canvas.
A arquitetura segue o padrao Game Loop com objetos-entidade e sistemas
centralizados em uma classe Game orquestradora.

ARQUITETURA EM CAMADAS:

  [INPUT LAYER] --> [GAME LOOP] --> [UPDATE] --> [RENDER]
       |                |               |             |
  keydown/keyup    loop(now)      update(dt)    render()
  objeto keys      requestAnim     todos os      canvas 2D
  listeners DOM    Frame           sistemas      context

O jogo e single-threaded, executando em um loop continuo via
requestAnimationFrame. Nao ha workers, backend, ou rede.

DIAGRAMA DE DEPENDENCIAS ENTRE OBJETOS PRINCIPAIS:

  Game (orquestrador)
  |-- Player (controlado por input)
  |-- MonsterEntity (IA autonoma, referencia Game)
  |-- DoorEntity[] (entidades passivas)
  |-- ArtifactEntity[] (entidades passivas)
  |-- Particle[] (particulas efemeras)
  |-- tiles[][] (matriz de caracteres ASCII)
  |-- visibilityGrid[][] / visibilityAge[][] (fog of war)
  |-- keys{} (objeto global de teclas pressionadas)
  |-- DOM elements (HUD, paineis, botoes)

================================================================================
4. FLUXO COMPLETO DO GAME LOOP
================================================================================

O game loop e implementado no metodo Game.loop(now):

  loop(now) {
    dt = min((now - lastTime) / 1000, 0.1)   // delta time em segundos, cap 100ms
    lastTime = now
    update(dt)
    render()
    requestAnimationFrame(loop)
  }

DELTA TIME (dt):
  - Calculado como diferenca entre timestamps de requestAnimationFrame (ms)
  - Convertido para segundos (divisao por 1000)
  - Limitado a 0.1 (100ms) para evitar espasmos de fisica se a aba ficar
    em background
  - Todas as velocidades, timers e animacoes sao multiplicadas por dt

ORDEM DE ATUALIZACAO (update):
  1. Portas (doorEntities) - animacoes, debounce
  2. Player - movimento, colisao, interacao
  3. MonsterEntity - IA (FSM), ataque
  4. ArtifactsEntity - animacao de glow
  5. Particulas - movimento e remocao de expiradas
  6. Mensagens - timer de exibicao
  7. Transicao dia/noite - roof alpha, nightTransition
  8. Delay de summon - contagem regressiva para spawn do monstro
  9. Game state - verifica se todos artefatos foram coletados
  10. Camera - segue o player no centro do canvas
  11. Visibilidade - fog of war, raycasting
  12. HUD - atualizacao do HTML do painel

ORDEM DE RENDERIZACAO (render):
  1. clearRect - limpa o canvas
  2. Background preto #111
  3. renderTiles - todos os tiles do mapa (com camX/camY offset)
  4. renderArtifacts - glow dos artefatos sobre o chao
  5. renderRoof - overlay escuro sobre interior (se player fora)
  6. player.render - circulo azul com olhos
  7. monster.render - esfera roxa com chapeu, olhos, indicador
  8. renderParticles - particulas 2x2
  9. renderFog - overlay preto semi-transparente sobre tiles nao visiveis
  10. renderNight - vignette radial escura
  11. renderDebug - (se debugMode) waypoints, estado IA, cone de visao, FPS
  12. renderMessage - atualiza DOM do elemento #message
  13. renderInteractionBar - atualiza DOM da barra de progresso

CANVAS:

SISTEMA DE CAMADA (PAINTER'S ALGORITHM):

  Camada 0: Background solido (#111)
  Camada 1: Tiles do mapa (parede, chao, grama, porta, altar, furniture)
  Camada 2: Artefatos (glow pulsante)
  Camada 3: Telhado (overlay escuro sobre interior)
  Camada 4: Player (circulo azul)

  Camada 6: Particulas (quadrados 2x2 coloridos)
  Camada 7: Fog of War (overlay preto semi-transparente)
  Camada 8: Night vignette (gradiente radial escuro)
  Camada 9: Debug (waypoints, textos, cone de visao - apenas debugMode)

FRUSTUM CULLING:
  Em renderTiles, cada tile e verificado contra os limites do canvas com
  margem de 50px. Tiles fora da viewport sao pulados:
    if (sx + TILE_SIZE < -50 || sx > canvas.width + 50 ||
        sy + TILE_SIZE < -50 || sy > canvas.height + 50) continue;

6. SISTEMA DE CAMERA
================================================================================

A camera e um offset (camX, camY) que centraliza o player no canvas.

  updateCamera() {
    camX = player.px - (mapWidth * TILE_SIZE / 2)
    camY = player.py - (mapHeight * TILE_SIZE / 2)
  }

Todo elemento renderizado subtrai camX/camY da sua posicao mundial:
  screenX = worldX - camX
  screenY = worldY - camY

Isso cria o efeito de camera seguindo o player. Nao ha limites de clamp.


================================================================================
7. SISTEMA DE COLISAO
================================================================================

COLISAO DO PLAYER (Player.canMoveTo, linha 471):

  Algoritmo: 4-point corner collision check com margem de 4px.

  Para a posicao candidata (px, py), verifica 4 cantos com offset de 4px:
    (px-4, py-4)  (px+4, py-4)
    (px-4, py+4)  (px+4, py+4)

  Para cada canto, converte para coordenada de tile (divisao inteira por
  TILE_SIZE) e verifica:

  - Se fora dos limites do mapa -> colide
  - Se tile === 'O' (parede) -> colide
  - Se tile === 'W' (furniture) -> colide
  - Se tile === 'd' (porta):
      Busca a DoorEntity na posicao. Se door.solid === true -> colide.
      door.solid retorna true quando porta fechada (!open) OU
      durante a animacao (animating).

  Movimento e feito por eixo separadamente (move X, depois move Y),
  permitindo deslizar ao longo de paredes.

COLISAO DO MONSTRO (MonsterEntity.canMoveTo, linha 690):

  Identico ao player, mas com margem de 3px (ligeiramente menor).
  O pathfinding BFS ja garante que o monstro so tenta se mover
  para tiles validos. A verificacao de colisao e uma camada extra.


================================================================================
8. ESTRUTURA DO MAPA
================================================================================

O mapa e definido como uma matriz de caracteres ASCII (tiles[y][x]).

DIMENSOES DO MAPA DEFAULT:
  Largura: 37 tiles
  Altura:  18 tiles
  Resolucao: 1184 x 576 pixels (37*32 x 18*32)

SIMBOLOS E SEUS SIGNIFICADOS NO GAMEPLAY:

  O = Wall (parede solida)
      Bloqueia movimento, visao (raycasting), pathfinding
      Cor: marrom escuro (#5c3a1e)

  C = Floor (chao interior)
      Passavel, nao bloqueia nada
      Cor: bege madeira (#c4a67a)

  G = Grass (grama)
      Passavel, exterior
      Cor: verde (#3a7a2a)
      Player nesta area -> telhado cobre interior
      Padding: linhas mais curtas sao preenchidas com 'G' pelo parser

  d = Door (porta)
      Comportamento dinamico (aberta = passavel, fechada = solida)
      Cor: dourado fechada (#8b6914), marrom aberta (#4a3a0a)
      Cada 'd' gera uma instancia DoorEntity
      Interagivel com tecla E, monstro abre automaticamente

  A = Altar (altar de summon)
      Passavel, interagivel
      Cor: vermelho (#ff4444)
      Funcao: ponto onde o player realiza o ritual (hold E 4s)

  P = Player Spawn
      Ponto de spawn do jogador. Apenas 1 P valido.

  M = Monster Spawn
      Ponto onde o monstro aparece ao ser invocado.

  F = Artifact Spawn
      Ponto de spawn de artefato. Cada F gera uma ArtifactEntity.
      Quantidade de F tiles define a dificuldade inicial.

  U = Waypoint
      Ponto de patrulha do monstro.
      Invisivel em gameplay normal, visivel no modo debug.
      Nao tem colisao propria.

  W = Furniture (obstaculo solido interno)
      Bloqueia movimento e pathfinding
      Cor: cinza (#666666)

PARSING DO MAPA (parseMap, linha 282):

  Entrada: string de texto com multiplas linhas
  Processamento:
    1. Split por '\n', filtra linhas vazias
    2. Remove TODOS os espacos (replace(/ /g, ''))
    3. Determina largura maxima entre todas as linhas
    4. Padroniza: linhas mais curtas recebem 'G' no final
    5. Valida cada caractere contra o Set de 10 simbolos validos.
       Caracteres invalidos sao substituidos por 'C' (floor) com console.warn
    6. Durante a varredura, coleta em arrays separados:
       - doors[]: posicoes {x,y} de 'd'
       - artifacts[]: posicoes {x,y} de 'F'
       - waypoints[]: posicoes {x,y} de 'U'
       - altarPos: posicao de 'A' (ultimo encontrado)
       - playerSpawn: posicao de 'P' (ultimo encontrado)
       - monsterSpawn: posicao de 'M' (ultimo encontrado)

  Retorno: objeto {
    tiles, doors, artifacts, waypoints,
    altarPos, playerSpawn, monsterSpawn,
    width, height
  }

  Fallbacks:
    - playerSpawn: se nao encontrado, usa {x:1, y:1}
    - monsterSpawn: se nao encontrado, usa altarPos; se tambem null, {x:2, y:2}
    - artifactCount: se 0 artefatos no mapa, define 3 como default

9. SISTEMA DE PORTAS
================================================================================

CLASSE: DoorEntity (linha 361)

ATRIBUTOS:
  tileX, tileY      - posicao no grid (imutavel)
  open              - boolean, estado atual (false = fechada)
  animating         - boolean, true durante transicao
  animTimer         - float, progresso da animacao em segundos
  animDuration      - float, duracao total da animacao (0.4s)
  debounceTimer     - float, cooldown apos animacao terminar (0.3s)
  animProgress      - float [0-1], 0=fechada, 1=aberta

ESTADOS DA PORTA:

  [FECHADA] --toggle()--> [ANIMANDO ABRINDO] --0.4s--> [ABERTA + DEBOUNCE]
  [ABERTA]  --toggle()--> [ANIMANDO FECHANDO]--0.4s--> [FECHADA + DEBOUNCE]

  Durante animacao: animating=true, solid=true (bloqueia passagem)
  Durante debounce (0.3s): toggle() ignorado (evita spam)

ANIMACAO (update, linha 372):

  if (animating) {
    animTimer += dt
    if (open)  animProgress = min(1, animTimer / animDuration)       // 0->1
    else       animProgress = max(0, 1 - animTimer / animDuration)   // 1->0
    if (animTimer >= animDuration) {
      animating = false
      debounceTimer = 0.3
      animProgress = open ? 1 : 0
    }
  }
  if (debounceTimer > 0) debounceTimer -= dt

TOGGLE (linha 388):
  So executa se !animating e debounceTimer <= 0
  Inverte open, inicia animacao (animating=true, animTimer=0)

FORCE OPEN (linha 394):
  Usado pelo monstro para abrir portas automaticamente
  So executa se porta fechada e nao animando. Chama toggle().

SOLID GETTER (linha 397):
  return !open || animating
  Porta e solida se fechada OU durante animacao

10. SISTEMA DE ARTEFATOS
================================================================================

CLASSE: ArtifactEntity (linha 403)

ATRIBUTOS:
  tileX, tileY    - posicao no grid
  collected        - boolean, true se ja foi coletado
  glowPhase        - float, fase da animacao de brilho (radianos)

ANIMACAO DE GLOW:
  update(dt): glowPhase += dt * 3  (3 rad/s, ~0.48 ciclos/s)
  render: glow = 0.5 + 0.5 * sin(glowPhase)

  Duas camadas de circulo:
  1. Circulo externo: raio TILE_SIZE * 0.3, alpha 0.3 + glow*0.7
  2. Circulo interno: raio TILE_SIZE * 0.12, alpha 1

SPAWN:
  Criados em loadMap() para cada tile 'F' encontrado

COLETA:
  Player segura E por 1.5 segundos proximo ao artefato
  Ao completar: collected=true, collectedArtifacts++,
  spawna 6 particulas ciano

RESPAWN:
  Quando todos os artefatos sao coletados (monstro morre):
  respawnArtifacts() reseta collected=false em todos.
  Se houver menos entidades que artifactCount, cria novas
  em posicoes 'F' aleatorias.


================================================================================
11. SISTEMA DO ALTAR
================================================================================

O altar e um ponto de interacao onde o player invoca o monstro.

LOCALIZACAO: tile 'A' no mapa. Posicao armazenada em game.altarPos.

INTERACAO:
  1. Player se aproxima do altar (distancia < 1.5 tiles)
  2. Player pressiona e segura E
  3. Barra de progresso enche por 4 segundos (interactDuration = 4)
  4. Ao completar 4s:
     - summoning = true
     - summonDelay = 3 (3 segundos de delay)
     - Mensagem: "Summoning ritual begins..."
  5. Apos 3 segundos de delay:
     - spawnMonster() e chamado
     - summonCount incrementa
     - monster.speed = 70 + (summonCount - 1) * 10
     - monster.spawn() - ativa o monstro, inicia patrulha

CONDICAO: O altar so pode ser usado se o monstro NAO estiver vivo
  (game.monster.alive === false).

FLUXO DE ESTADOS DO ALTAR:

  [ALTAR INATIVO] --hold E 4s--> [RITUAL INICIADO] --3s delay--> [MONSTRO SPAWNA]
  [MONSTRO VIVO] --coleta todos artefatos--> [MONSTRO MORRE] --> [ALTAR INATIVO]


================================================================================
12. MAQUINA DE ESTADOS DO MONSTRO
================================================================================

O monstro implementa uma FSM (Finite State Machine) com 3 estados.

ESTADOS:
  'patrol'  - Patrulhando waypoints em ordem (sorteada aleatoriamente)
  'chase'   - Perseguindo o player ativamente
  'search'  - Indo ate a ultima posicao conhecida do player

TRANSICOES:

  PATROL -> CHASE:
    canDetectBehind() retorna true (player muito perto por tras)
    canSeePlayer() retorna true (player no cone de visao com LOS)
    Ao entrar: chaseTimer = 0, path = null

  CHASE -> SEARCH:
    Nao consegue ver o player (nem cone, nem deteccao traseira)
    chaseTimer > 1.0 segundo
    Ao entrar: salva lastKnownPlayerPos, searchTimer = 0, path = null

  CHASE -> PATROL:
    Player morreu (!game.player.alive)
    Ao entrar: path = null

  SEARCH -> CHASE:
    canSeePlayer() ou canDetectBehind() voltam a detectar
    Ao entrar: chaseTimer = 0, path = null

  SEARCH -> PATROL:
    searchTimer > 2.0s (timeout)
    lastKnownPlayerPos e null
    Chegou ao destino (followPath retorna false)
    Nao foi possivel calcular caminho
    Ao entrar: path = null

DIAGRAMA DE TRANSICOES:

                    +--(ve player)---> CHASE ---(perde visao 1s)---> SEARCH
                    |                    |  ^                          |
  PATROL -----------+                    |  |---(re-ve player)---------|
       ^                                |                             |
       |---(player morto)---------------|                             |
       |                                                              |
       +----(timeout 2s / chegou / sem caminho)----------------------+

VARIAVEIS DE CONTROLE DA FSM:
  state              - string: 'patrol' | 'chase' | 'search'
  chaseTimer         - float: tempo sem ver o player durante chase
  searchTimer        - float: tempo gasto no estado search
  lastKnownPlayerPos - {x,y}|null: ultima posicao conhecida do player
  path               - [{x,y}]|null: caminho BFS atual
  pathTarget         - int|string|null: identificador do alvo do path
  pathRecalc         - float: timer para recalcular path no patrol


================================================================================
13. SISTEMA DE VISAO DO MONSTRO
================================================================================

O monstro possui dois metodos de deteccao do player.

DETECCAO POR CONE DE VISAO (canSeePlayer, linha 633):

  Condicoes para detectar:
  1. Player esta vivo
  2. Distancia euclidiana <= 250 pixels (~7.8 tiles)
  3. Player dentro do cone de 180 graus frontal
     (exceto se distancia <= 50 pixels - ve em qualquer direcao)
  4. Linha de visao desobstruida (hasLineOfSight)

  Calculo do cone:
    angleToPlayer = atan2(player.py - monster.py, player.px - monster.px)
    diff = angleToPlayer - facingAngle
    Normaliza diff para [-PI, PI]
    Se |diff| > PI/2 (90 graus) E distancia > 50 -> fora do cone

DETECCAO TRASEIRA (canDetectBehind, linha 647):

  Condicoes:
  1. Player esta vivo
  2. Distancia euclidiana <= 45 pixels (~1.4 tiles)
  3. Player no setor traseiro: |angleToPlayer - facingAngle| > 0.65*PI
     (~117 graus do facing)

LINHA DE VISAO (hasLineOfSight, linha 661):

  Algoritmo: Bresenham Line Algorithm em coordenadas de tile.

  Percorre cada tile na linha reta entre origem e destino:
  - Se tile === 'O' (parede) -> bloqueada, retorna false
  - Se tile === 'd' (porta) -> verifica door.solid; se solida -> bloqueada

  Retorna true se nenhum obstaculo encontrado no caminho.


================================================================================
14. SISTEMA DE BUSCA E PERSEGUICAO (PATHFINDING)
================================================================================

O monstro usa o algoritmo BFS (Breadth-First Search) para encontrar o menor
caminho ate o alvo, desviando de paredes e moveis.

ALGORITMO BFS: Game.findPath(sx, sy, gx, gy) - linha 1187

  Complexidade: O(W*H) onde W=mapWidth, H=mapHeight
  Para o mapa default (37x18): maximo 666 tiles visitados

  Funcionamento:
  1. Se origem == destino, retorna [{x:gx, y:gy}]
  2. Valida bounds de origem e destino
  3. Inicializa matrizes visited[height][width] e parent[height][width]
  4. Usa fila com pointer head para O(1) dequeue:
     - Adiciona origem, marca visited
     - Enquanto fila nao vazia: desenfileira, se for destino reconstroi
       caminho via parent e retorna array
     - Para cada vizinho (4-direcoes):
       Pula se fora dos bounds, visited, ou tile === 'O'/'W'
       Portas ('d') sao transitaveis (monstro pode abri-las)
       Marca visited, registra parent, enfileira
  5. Se fila esgotar: retorna null (sem caminho)

SEGUIMENTO DE CAMINHO: MonsterEntity.followPath(dt) - linha 750

  Para cada frame:
  1. Pega o primeiro tile do path (path[0])
  2. Calcula vetor direcao ate o centro daquele tile
  3. Se distancia < TILE_SIZE * 0.25 (8 pixels): remove path[0],
     avanca para proximo tile (recursao)
  4. Senao: move na direcao com velocidade speed (patrol/search)
     ou speed * 1.4 (chase)
  5. Atualiza facingAngle para direcao do movimento
  6. Verifica colisao via canMoveTo antes de mover

  Retorna: true se ainda ha tiles no path, false se chegou ao destino.

COMPORTAMENTO POR ESTADO:

  PATROL:
    Recalcula caminho a cada 0.5s ou quando waypoint muda
    Se findPath retorna null: pula para proximo waypoint
    Ao chegar: currentWaypoint++, se esgotou gera nova ordem

  CHASE:
    Recalcula caminho TODO frame ate o tile do player
    Se player morre: volta para PATROL

  SEARCH:
    Calcula caminho UMA vez ao entrar no estado
    Se nao ha caminho: volta para PATROL
    Segue path ate o fim ou timeout (2s)


================================================================================
15. SISTEMA DE WAYPOINTS
================================================================================

Waypoints sao pontos de patrulha do monstro, definidos por tiles 'U' no mapa.

ESTRUTURA DE DADOS:
  game.waypoints: [{x, y}, ...] - array de coordenadas de tile
  monster.waypointOrder: [int, ...] - permutacao aleatoria de indices
  monster.currentWaypoint: int - indice em waypointOrder do waypoint atual

GERACAO DE ORDEM (generateWaypointOrder, linha 621):
  Fisher-Yates shuffle:
    indices = [0, 1, 2, ..., n-1]
    for i = n-1 downto 1:
      j = random(0, i)
      swap(indices[i], indices[j])

FLUXO DE PATRULHA:
  1. Gera ordem aleatoria de waypoints
  2. Vai para waypointOrder[0]
  3. Ao chegar: currentWaypoint++
  4. Continua ate waypointOrder[n-1]
  5. Ao completar: gera nova ordem aleatoria (loop infinito)

INTERRUPCAO: Se o monstro detectar o player, transita para CHASE.
Ao voltar para PATROL, continua do waypoint onde parou.


================================================================================
16. SISTEMA DE FOG OF WAR
================================================================================

O Fog of War controla quais tiles sao visiveis para o player.

ESTRUTURAS DE DADOS:
  visibilityGrid[height][width]: int
    0 = nunca visto (preto opaco)
    1 = visto anteriormente, nao visivel agora (preto semi-transparente)
    2 = visivel agora (sem overlay)

  visibilityAge[height][width]: float [0-1]
    Quanto tempo resta antes do tile ser esquecido.
    1 = recem visto, 0 = esquecido.

ATUALIZACAO (updateVisibility, linha 1124):

  Se debugMode ativo:
    Define TODOS visibilityGrid = 2 e retorna.

  Se debugMode inativo:

  FASE 1 - AGING:
    Para cada tile:
      Se visibilityAge > 0:
        age -= fogDecay * 0.02
          Dia (fogDecay=0.4): age reduz 0.008/frame
          Noite (fogDecay=0.15): age reduz 0.003/frame
        Se age <= 0: zera age e visibilityGrid = 0
        Senao se visibilityGrid == 2: muda para 1 (visto anteriormente)
      Senao se visibilityGrid > 0 (age==0 mas ainda visivel):
        Reseta visibilityGrid = 0 (correcao de bug do debug mode)

  FASE 2 - RAYCASTING:
    Raio: Dia=12 tiles, Noite=5 tiles
    Para cada tile dentro do raio circular:
      Se hasLineOfSight(player, tile): visibilityGrid=2, visibilityAge=1

RENDERIZACAO DO FOG (renderFog, linha 1482):
  Se visibilityGrid >= 2: pula (totalmente visivel)
  Se visibilityGrid == 1: overlay rgba(0,0,0,0.6)
  Se visibilityGrid == 0: overlay rgba(0,0,0,0.92)

17. SISTEMA DE DIA/NOITE
================================================================================

O ciclo dia/noite esta vinculado ao estado do monstro.

VARIAVEIS:
  isNight: boolean - true quando monstro vivo por tempo suficiente
  nightTransition: float [0-1] - transicao suave dia (0) -> noite (1)

LOGICA DE TRANSICAO (Game.update):

  Monstro vivo E ainda nao e noite:
    nightTransition += dt * 0.8     // sobe a 0.8/s
    Quando nightTransition >= 1: isNight = true

  Monstro NAO vivo E e noite:
    nightTransition -= dt * 1.2     // desce a 1.2/s
    Quando nightTransition <= 0: isNight = false

  Monstro NAO vivo, nao e noite, mas nightTransition > 0:
    nightTransition -= dt * 1.2     // termina de descer

EFEITOS:
  Dia: raio de visao 12 tiles, fog decay 0.4, sem vignette
  Noite: raio de visao 5 tiles, fog decay 0.15, vignette radial escura

RENDERIZACAO DA NOITE (renderNight, linha 1499):
  Gradiente radial centrado no canvas:
    Centro (30%): rgba(0,0,0,0) - transparente
    Meio (50%): rgba(0,0,30, nightTransition*0.3)
    Borda (100%): rgba(0,0,0, nightTransition*0.7)
  Intensidade proporcional a nightTransition.

18. SISTEMA DE TELHADO (ROOF SYSTEM)
================================================================================

O telhado cobre o interior da casa quando o player esta do lado de fora.

CALCULO DE ALPHA (computeRoofAlpha, linha 1099):

  Se debugMode: retorna 0 (telhado invisivel)

  Detecta se player esta dentro ou fora:
    Se tile != 'G' e != 'O': player dentro -> retorna 0

  Player fora:
    Para cada porta aberta (open=true, !animating):
      dist = sqrt((door.x - player.tileX)^2 + (door.y - player.tileY)^2)
      Se dist < 3: retorna max(0, (dist-1)/2)
      (gradiente: perto=0, longe=1)
    Se nenhuma porta aberta proxima: retorna 1

SUAVIZACAO:
  roofAlpha += (targetRoofAlpha - roofAlpha) * min(dt * 4, 1)
  Interpolacao linear com speed 4/s.

RENDERIZACAO (renderRoof, linha 1448):
  Se roofAlpha <= 0.01: nao renderiza
  Para cada tile interior (!= 'G', != 'O'):
    Se perto de porta aberta (Manhattan <= 2): alpha * 0.3
    Senao: alpha * 0.85
    Desenha retangulo rgba(30,20,15, alpha)

26. ESTRUTURA MATEMATICA
================================================================================

FUNCOES MATEMATICAS USADAS:

1. Distancia Euclidiana: dist = sqrt(dx^2 + dy^2)
   Usada em: interacao, deteccao, perseguicao

2. Normalizacao de vetor: ndx = dx/dist, ndy = dy/dist
   Usada em: movimento, pathfinding

3. Angulo entre pontos: angle = atan2(dy, dx)
   Usada em: visao do monstro, direcao

4. Normalizacao de angulo para [-PI, PI]:
   while (diff > PI) diff -= 2*PI
   while (diff < -PI) diff += 2*PI
   Usada em: cone de visao

5. Interpolacao linear: value += (target - value) * min(dt*speed, 1)
   Usada em: roof alpha

6. Bresenham Line Algorithm:
   Percorre tiles em linha reta para raycasting de visao

7. BFS (Breadth-First Search):
   Fila com pointer head. 4 vizinhos. Reconstroi caminho via parent.
   Usada em: pathfinding do monstro

8. Fisher-Yates Shuffle:
   for i = n-1 downto 1: j = random(0,i); swap(arr[i], arr[j])
   Usada em: ordem de waypoints

9. Oscilacao senoidal: glow = 0.5 + 0.5*sin(phase)
   Usada em: glow de artefatos

10. Mapeamento tile <-> pixel:
    tileX = floor(pixelX / TILE_SIZE)
    pixelX = tileX * TILE_SIZE + TILE_SIZE/2

31. FLUXO COMPLETO DE GAMEPLAY
================================================================================

FASE 1 - EXPLORACAO (DIA):
  Monstro nao existe. Ambiente claro, visao ampla (12 tiles).
  Player explora, entra na casa pelas portas.
  Telhado cobre interior quando player esta fora.

  Apos 3 segundos de delay, monstro spawna no tile 'M'.

  Monstro ativo: patrulha waypoints.
  Ambiente escurece (~1.25s). Visao reduzida (5 tiles).
  Player coleta todos os artefatos (hold E 1.5s cada).
  Monstro detecta player -> persegue (chase speed 1.4x).
  Player perde 20 HP/hit (cooldown 1s). 100 HP total.

FASE 4 - VITORIA:
  Todos artefatos coletados -> monstro morre.
  Ambiente clareia (~0.83s).
  Artefatos reaparecem nos pontos 'F'.

FASE 5 - REPETICAO:
  Player invoca novamente. summonCount++.
  Monstro mais rapido: speed = 70 + (summonCount-1)*10.
  Ciclo reinicia da Fase 2.

SECAO 51 — SISTEMA DE MENSAGEM SEQUENCIAL AO SUMMONAR MONSTRO
================================================================================

51.1 — CONCEITO

   Ao summonar um monstro (apos completar ritual no altar), o jogo
   exibe uma sequencia de duas fases de mensagem para informar o
   jogador sobre o tipo de monstro que foi invocado:

   FASE 1 (2s, centro da tela):
     Exibe "<Nome> ouviu voce. Corra." no elemento #message (DOM).
     Usa o sistema existente showMessage() para exibir o texto.

   FASE 2 (3s, acima da hotbar):
     Exibe a descricao do monstro (mt.desc) no novo elemento
     #summon-desc, posicionado acima da barra de itens (hotbar).
     Nao bloqueia mensagens normais (showMessage).

   A transicao entre fases e automatica e controlada por
   summonPhase e summonPhaseTimer no Game.update().

51.2 — ESTRUTURA DE DADOS

   Game.summonPhase: string ('' | 'name' | 'desc')
     Estado atual da sequencia. '' = inativo, 'name' = exibindo
     nome no centro, 'desc' = exibindo descricao acima da hotbar.

   Game.summonPhaseTimer: number (segundos)
     Contagem regressiva da fase atual. Decrementado por dt
     em Game.update().

   Game.summonPhaseMessage: string
     Texto da fase 1 (ex: "Glitch ouviu voce. Corra.").

   Game.monsterDesc: string
     Texto da fase 2 (ex: "It appears from unpredictable locations
     and moves unnaturally fast.").

51.3 — ELEMENTOS DOM ENVOLVIDOS

   #message (existente):
     Centro da tela (top: 50%, left: 50%, transform: translate(-50%,-50%)).
     Fonte: 29px (aumentada de 24px, +20%).
     Usado pela fase 1 e por todas as mensagens normais do jogo.

   #summon-desc (novo):
     Acima da hotbar (bottom: 80px, left: 50%, transform: translateX(-50%)).
     Fonte: 18px, cor: #fff.
     Usado exclusivamente pela fase 2 (descricao do monstro).

51.4 — FLUXO COMPLETO

   1. Player completa interacao no altar -> summonDelay = 3
   2. Durante summonDelay: "Summoning ritual begins..." (showMessage)
   3. summonDelay chega a 0 -> spawnMonster() chamado
   4. spawnMonster() define summonPhase = 'name',  summonPhaseTimer = 2.0,
      summonPhaseMessage = nome + ' ouviu voce. Corra.',
      monsterDesc = mt.desc, showMessage(summonPhaseMessage)
   5. Game.update() decrementa summonPhaseTimer
   6. Quando summonPhaseTimer <= 0 (2s):
      summonPhase = 'desc', summonPhaseTimer = 3.0,
      showMessage('') limpa centro, showSummonDesc(monsterDesc) exibe
      descricao acima da hotbar
   7. Game.update() decrementa summonPhaseTimer novamente
   8. Quando summonPhaseTimer <= 0 (3s):
      summonPhase = '', hideSummonDesc() esconde descricao,
      monsterDesc = '', summonPhaseMessage = '' limpos
   9. Sistema em repouso ate o proximo summon

51.5 — COEXISTENCIA COM MENSAGENS NORMAIS

   Durante a fase 2, mensagens normais (showMessage) continuam
   funcionando normalmente no centro da tela. O elemento #summon-desc
   e um elemento DOM separado e nao interfere com o #message.

   Exemplo: Durante os 3s da descricao, o jogador coleta um artefato.
   "Artifact collected! (1/3)" aparece no centro, enquanto a descricao
   permanece visivel acima da hotbar.

51.6 — ESCALABILIDADE

   Para adicionar uma nova fase:
     1. Adicionar novo valor a summonPhase (ex: 'warning')
     2. Em Game.update(), adicionar nova condicao no if/else
     3. Criar novo elemento DOM se necessario
     4. Definir timer e transicao

   Para modificar textos:
     Alterar spawnMonster() onde summonPhaseMessage e monsterDesc
     sao definidos.

   Para modificar duracoes:
     Alterar summonPhaseTimer = 2.0 e summonPhaseTimer = 3.0 em
     spawnMonster() e Game.update().

51.7 — INICIALIZACAO E RESET

   Construtor: summonPhase = '', summonPhaseTimer = 0,
   summonPhaseMessage = '', monsterDesc = ''

   loadMap(): mesmo reset. Garante que ao reiniciar o jogo ou
   carregar novo mapa, nenhuma mensagem residual permaneca.

ALTERACAO 10 - SISTEMA DE ILUMINACAO DINAMICA POR RAYCAST

  SUBSTITUICAO DO FOG OF WAR:
    Sistema antigo: visibilityGrid[][] com valores 0/1/2 + renderFog()
    com retangulos pretos semi-transparentes por tile. Iluminacao
    baseada em grid, sem sombras continuas.

    Sistema novo: raycasting radial 360 graus + lightmap canvas
    com visibilidade poligonal continua. Sombras reais bloqueadas
    por paredes e portas fechadas.

  ARQUITETURA DO NOVO SISTEMA:
    Game.castRay(px, py, dx, dy, maxDist):
      Raycast DDA com step de 3 pixels
      Avanca ate encontrar parede (O/W) ou porta fechada (d solid)
      Retorna ponto de colisao {x, y} no espaco do mundo

    Game.buildVisibilityPolygon(player):
      Emite 220 raios (dia) ou 360 raios (noite) em circulo completo
      Alcance: 384px (dia) / 160px (noite)
      Aplica jitter (2px + senoidal) nos pontos finais para bordas suaves
      Retorna array de pontos {x, y} formando poligono de visibilidade

    Game.buildLightmap():
      Canvas offscreen (lightmapCanvas) do tamanho do canvas do jogo
      Preenche com escuridao (alpha variavel por dia/noite)
      Para cada jogador vivo:
        - Clip pela visibilidade poligonal (ctx.clip())
        - Gradiente radial: transparente no centro, escuro nas bordas
        - Glow suave ao redor do jogador (destination-out)
      Retorna o canvas para ser desenhado sobre o jogo

    Game.isPointVisible(px, py):
      Point-in-polygon test (even-odd rule) contra todos os poligonos
      de visibilidade dos jogadores vivos
      Retorna true se (px, py) esta dentro de qualquer poligono

  RENDER PIPELINE (NOVA ORDEM):
    1. Background + Tiles + Artifacts + Roof
    2. buildLightmap() -> drawImage sobre o canvas
    3. renderDoors() (sempre visiveis, sobre a escuridao)
    4. Players + Monsters + Particles (com isPointVisible check)
    5. renderNight() (vignette atmosferico)
    6. renderDebug() (raios, poligonos, FPS)

  MATEMATICA DOS RAYCASTS:
    Ray: (px + cos(angle)*t, py + sin(angle)*t) para t em [0, maxDist]
    Step: 3 pixels por iteracao
    Tile check: floor(x/TILE_SIZE), floor(y/TILE_SIZE)
    Bloqueio: tile === 'O' || tile === 'W' || (tile === 'd' && door.solid)
    Ao detectar bloqueio: retrocede um step (x -= dx*step, y -= dy*step)
    Resultado: coordenadas continuas do ponto de impacto

  POINT-IN-POLYGON (EVEN-ODD RULE):
    Para cada aresta (pts[i], pts[j]) do poligono:
      Se a aresta cruza a linha horizontal em py:
        intersecao = (xj - xi) * (py - yi) / (yj - yi) + xi
        Se px < intersecao: inverte flag inside
    Otimizacao: O(N) por verificacao, N = 220-360 pontos

  PERFORMANCE:
    Por frame (1 jogador, dia):
      - 220 raycasts * ~64 steps = ~14,080 tile checks
      - buildLightmap: 1 clearRect + 1 fillRect + clip + gradiente
      - isPointVisible: N/A (nao chamado se jogador visivel no proprio poligono)
    Por frame (2 jogadores, dia):
      - 440 raycasts * ~64 steps = ~28,160 tile checks
    Por frame (1 jogador, noite):
      - 360 raycasts * ~27 steps = ~9,720 tile checks
    LightmapCache: canvas offscreen reutilizado, recriado apenas se
    dimensoes mudarem (mudanca de mapa)

  OTIMIZACOES:
    - Step de 3px reduz ~3x comparado a step de 1px
    - Canvas offscreen reutilizado entre frames
    - Menos raios durante o dia (220 vs 360)
    - Raycasts sao puramente locais, sem alocacao de arrays grandes
    - isPointVisible so chamado para entidades (monstros, players)
      que estao proximas da camera

  DETALHES DO LIGHTMAP:
    nightAlpha = 0.88 + nightTransition * 0.07
      Dia:   alpha = 0.88 (escuridao base)
      Noite: alpha = 0.95 (mais escuro)
    Gradiente radial por jogador:
      0%:     transparente (centro iluminado)
      35%:    transparente (area bem iluminada)
      70%:    alpha 0.4 (transicao)
      100%:   alpha 0.88 (borda escura)
    Glow: destination-out com gradiente pequeno (12% do raio max)
      Suaviza a transicao no centro do poligono

  ENTITY VISIBILITY:
    MonsterEntity.render(): retorna cedo se !isPointVisible(px, py)
      Exceto: debug mode OU Oracle com Reveal Monster ativo
    Player.render(): retorna cedo se !isPointVisible(px, py)
      Exceto: debug mode
    Oracle Reveal: mostra monstro com highlight amarelo mesmo
      fora da area iluminada

  MULTIPLAYER LIGHTING:
    buildLightmap() processa TODOS os jogadores vivos
    Cada jogador contribui com seu poligono de visibilidade
    isPointVisible() verifica TODOS os poligonos (uniao)
    Resultado: area iluminada = uniao das visoes de todos

  DEBUG MODE (F1):
    Desenha outline do poligono de visibilidade (amarelo semi-transp)
    Pontos de colisao dos raycasts (quadrados amarelos a cada ~10 raios)
    Linhas dos raycasts do jogador ate os endpoints
    Contador de raios totais no canto inferior
    isPointVisible sempre retorna true (mapa totalmente visivel)

  IMPACTO NOS SISTEMAS EXISTENTES:
    updateVisibility(): removido do game loop (nao mais necessario)
      Metodo mantido no codigo para referencia, mas nao chamado
    renderFog(): removido do render pipeline
      Substituido por buildLightmap() + ctx.drawImage()
    visibilityGrid[][]: ainda inicializado em loadMap(), nao mais usado

SECAO 47 - SISTEMA DE AUTOTILING VISUAL

  47.1 - CONCEITO

    Sistema procedural que analisa vizinhanca de cada tile para gerar
    variacoes visuais. Elimina aparencia de grid repetitivo sem alterar
    colisao ou gameplay. Totalmente canvas-based, sem assets externos.

  47.2 - CACHE DE AUTOTILING

    tileVariation[height][width]: Float [0-1]
      Valor pseudo-aleatorio por tile baseado em hash da posicao
      Formula: ((x * 374761393 + y * 668265263) ^ 0x5bf03635) % 1000 / 1000
      Consistente entre frames (hash, nao Math.random)

    tileEdgeMask[height][width]: Int (bitmask 4 bits)
      Bit 0 (1): vizinho acima e de tipo diferente
      Bit 1 (2): vizinho abaixo e de tipo diferente
      Bit 2 (4): vizinho esquerda e de tipo diferente
      Bit 3 (8): vizinho direita e de tipo diferente
      Calculado uma vez em loadMap() para grass (G) e floor (C)

  47.3 - VARIACOES DE GRAMA (G)

    Cor base: #3a7a2a (verde)
    Variacao por hash: desloca matiz em +/- 8%, saturação em +/- 5%
    Borda contra floor (C) ou wall (O): escurece levemente
    Detalhes: pequenos pontos/linhas em tons variados de verde
    Waypoints (U): sub-tile com tom levemente mais escuro (trilha)

  47.4 - VARIACOES DE CHAO (C)

    Cor base: #c4a67a (bege madeira)
    Variacao por hash: desloca brilho em +/- 4%
    Linhas de tabua: finas linhas horizontais com offset aleatorio
    Artefatos (F): leve brilho refletido no chao abaixo
    Waypoints (U): tom levemente mais desgastado

  47.5 - ALGORITMO DE HASH

    function tileHash(x, y):
      h = (x * 374761393 + y * 668265263) ^ 0x5bf03635
      h = ((h >> 16) ^ h) * 0x45d9f3b
      return (h >>> 0) % 1000 / 1000

    Vantagens:
      - Deterministico (mesmo valor todo frame para mesma posicao)
      - Nao requer armazenamento alem do cache inicial
      - Boa distribuicao pseudo-aleatoria

  47.6 - RENDERIZACAO

    renderTiles(ctx):
      Para cada tile, alem da cor base:
        - Aplica variacao de cor por tileVariation[y][x]
        - Se tileEdgeMask indica borda: desenha transicao sutil
        - Se tile === 'U' (waypoint): desenha marcacao no chao
        - Se tile === 'F' (artefact): desenha area marcada no chao
      Tudo feito com fillRect e fillStyle, sem operacoes caras

  47.7 - PERFORMANCE

    tileVariation e tileEdgeMask: arrays Float32Array/Int8Array
    Calculados UMA vez em loadMap() (O(W*H))
    Nao recalculados por frame
    renderTiles: operacoes extras minimas (apenas ajuste de cor)
    Impacto: < 2% do tempo de frame

  47.8 - DEBUG MODE (F1)

    Exibe informacao de autotiling:
      - Edge mask value em cada tile
      - Tipo de variacao aplicada
      - Hash value do tile

SECAO 49 — SISTEMA DE PORTAS DUPLAS (DOUBLE DOOR)
================================================================================

49.1 — CONCEITO

   Quando duas ou mais portas (tile 'd') estao ortogonalmente adjacentes
   (cima, baixo, esquerda, direita), elas automaticamente formam um GRUPO
   de portas. O grupo funciona como uma unica porta maior:

   - Interagir com qualquer porta do grupo abre/fecha TODAS as portas
   - Visualmente, o grupo e renderizado como uma unica porta grande
     no bounding box do grupo
   - O monstro ao abrir uma porta do grupo, abre todas
   - A colisao respeita o estado sincronizado (todas abertas ou todas
     fechadas)

   DIAGONAL NAO CONTA: Duas portas na diagonal (ex: (x,y) e (x+1,y+1))
   NAO formam grupo. Apenas vizinhanca nas 4 direcoes ortogonais.

49.2 — ESTRUTURA DE DADOS

   DoorEntity.groupMembers: DoorEntity[] | null
     Array contendo TODAS as DoorEntity do mesmo grupo (incluindo a
     propria). null significa que a porta nao pertence a grupo nenhum.
     Exemplo: se portas A, B, C sao um grupo, entao:
       A.groupMembers = [A, B, C]
       B.groupMembers = [A, B, C]
       C.groupMembers = [A, B, C]

   DoorEntity.hasGroup(): boolean
     Retorna true se groupMembers nao for null e tiver length > 0.

49.3 — ALGORITMO DE AGRUPAMENTO (FLOOD-FILL)

   Executado uma vez em Game.loadMap() apos criar todas as DoorEntity.

   PASSO 1: Constroi mapa de posicoes (doorByPos) para O(1) lookup:
     doorByPos["tileX,tileY"] = DoorEntity

   PASSO 2: Para cada porta nao visitada, executa BFS:
     - Fila inicializada com a porta atual
     - Para cada porta na fila, verifica 4 vizinhos ortogonais
     - Se vizinho e uma porta (existe em doorByPos) e nao foi visitado,
       adiciona a fila
     - Ao final, component contem todas as portas do componente conexo

   PASSO 3: Se component.length >= 2 (tem pelo menos 2 portas):
     - Para cada porta no componente: door.groupMembers = component
     - Portas isoladas (component.length < 2): groupMembers = null

   COMPLEXIDADE: O(N) onde N = numero de portas no mapa.
   Executado apenas em loadMap(), nao por frame.

49.4 — PROPAGACAO DE TOGGLE

   DoorEntity.toggle(skipPropagation):
     - Se skipPropagation for false E groupMembers existir:
       Itera sobre groupMembers e chama member.toggle(true) em cada
       membro (exceto this)
     - Executa a logica normal: inverte open, inicia animacao

   DoorEntity.forceOpen():
     - Se groupMembers existir:
       Itera sobre groupMembers e chama member.toggle(true) em cada
       membro fechado e nao-animando (exceto this)
     - Chama toggle(true) em si propria

   Garantia: Todas as portas do grupo comecam a animacao no mesmo frame,
   mantendo-se sincronizadas visualmente.

49.5 — RENDERIZACAO DE GRUPO

   Game.renderDoors() detecta grupos e renderiza uma unica porta grande:

   BOUNDING BOX:
     minX = min(tileX dos membros)
     maxX = max(tileX dos membros)
     minY = min(tileY dos membros)
     maxY = max(tileY dos membros)
     Largura = (maxX - minX + 1) * TILE_SIZE
     Altura = (maxY - minY + 1) * TILE_SIZE

   FUNDO:
     INTERIOR_COLOR preenchendo todo o bounding box

   PORTA FECHADA:
     Grupo horizontal (width > height):
       - Porta ocupa 85% da largura, 70% da altura
       - Centralizada no bounding box
       - Puxador dourado no centro
     Grupo vertical (height > width):
       - Porta ocupa 70% da largura, 85% da altura
     Grupo quadrado (width == height, ex: 2x2):
       - Porta ocupa 80% da largura, 80% da altura

   ANIMACAO:
     Grupo horizontal: animProgress controla ALTURA (porta "sobe")
       doorH = altura * 0.7 * progress
       A porta encolhe de baixo para cima
     Grupo vertical: animProgress controla LARGURA (porta desliza)
       doorW = largura * 0.7 * progress
       A porta encolhe da direita para a esquerda

   PROXIMIDADE:
     Alcance base de 160px + metade da maior dimensao do grupo
     Garante que portas grandes sejam visiveis mesmo quando o centro
     esta alem do raio de visao noturno

49.6 — TELHADO E GRUPOS DE PORTAS

   computeRoofAlpha():
     Para portas agrupadas abertas, calcula distancia do player ate
     a borda mais proxima do bounding box do grupo (Manhattan).
     Se a distancia euclidiana para a borda < 3 tiles, reduz alpha.

   renderRoof():
     Para portas agrupadas abertas, tiles dentro do bounding box
     expandido (+2 tiles em cada direcao) recebem roofAlpha * 0.3
     em vez de roofAlpha * 0.85.

   Isso garante que entradas grandes (como portas duplas) tenham
   areas de transicao de telhado proporcionais ao seu tamanho.

49.7 — COMPORTAMENTO DO MONSTRO

   MonsterEntity.checkNearbyDoors():
     Quando o monstro chega perto de uma porta fechada que pertence a
     um grupo, forceOpen() propaga para todas as portas do grupo.
     Todas as portas do grupo abrem simultaneamente.

   Pathfinding (findPath):
     Tiles 'd' sao considerados transitaveis (sem verificacao de
     solid). O BFS de pathfinding nao precisa de modificacao.

   Colisao (canMoveTo):
     Cada porta individual mantem seu getter solid(). Como todas as
     portas do grupo abrem/fecham juntas, a colisao e consistente.

SECAO 50 — SISTEMA DE BASE DINAMICA PARA TILES ESPECIAIS (F, U, m)
================================================================================

50.1 — CONCEITO

   Tiles especiais F (Artifact Spawn), U (Waypoint) e m (Random Monster
   Spawn) sao posicionados no mapa ASCII, mas podem estar em areas de
   grama (exterior) ou de chao (interior). Anteriormente, todos eram
   tratados como INTERIOR_COLOR fixo. Agora, o sistema analisa os 8
   vizinhos de cada tile F/U/m e decide dinamicamente se o tile deve
   ser tratado como chao (C) ou grama (G).

   Esta decisao afeta:
   - Renderizacao visual (cor e autotiling)
   - Roof system (player dentro/fora)
   - Visao do player (indoor/outdoor range)
   - Edge mask no autotile cache

   DIAGONAIS SAO INCLUIDAS: A analise considera os 8 vizinhos (Moore
   neighborhood), incluindo diagonais, para maior precisao.

50.2 — ESTRUTURA DE DADOS

   Game.baseTileResolved[mapHeight][mapWidth]: string
     Array 2D populado uma vez em loadMap().
     Para tiles F, U, m: contem 'C' ou 'G' (resultado da resolucao).
     Para todos os outros tiles: contem o proprio tile original
     (this.tiles[y][x]).

50.3 — ALGORITMO DE RESOLUCAO

   Game.resolveBaseTile(x, y):
     1. Se tile nao for F, U ou m: retorna o proprio tile
     2. Para cada um dos 8 vizinhos (dx=-1..1, dy=-1..1, skip centro):
        - Se vizinho for 'C': floorCount++
        - Se vizinho for 'G': grassCount++
        - Se vizinho for 'd' (porta): floorCount++ (porta = ambiente interno)
        - Outros tiles (O, W, A, P, M, S, T, F, U, m): ignorados
     3. Retorna 'C' se floorCount >= grassCount, senao 'G'

   COMPLEXIDADE: O(1) por tile (8 vizinhos fixos).
   Executado O(W*H) vezes em loadMap() (uma vez).

50.4 — USO NOS SUBSISTEMAS

   Game.getEffectiveTile(x, y):
     Helper central. Retorna baseTileResolved[y][x] se existir,
     senao tiles[y][x]. Usado por todos os subsistemas.

   buildAutotileCache():
     Para cada tile, obtem tile resolvido de baseTileResolved.
     Se nao for 'C' nem 'G': edgeMask = 0 (sem autotiling).
     Para cada vizinho, compara com tile resolvido para determinar
     borda (mascara de bits: 1=cima, 2=baixo, 4=esq, 8=dir).

   renderTiles():
     Cor base: F/U/m usam baseTileResolved para escolher entre
     GRASS_COLOR e INTERIOR_COLOR.
     Autotiling: variavel effTile (tile efetivo) determina qual
     bloco de autotiling aplicar (floor ou grass).
     Marcacoes (waypoint, artifact glow): independentes do tile
     resolvido (sempre desenhadas em cima).

   computeRoofAlpha():
     Player sobre F/U/m resolvido como 'C': considerado dentro
     (roofAlpha = 0). Resolvido como 'G': considerado fora.

   updateVisionRanges():
     Player sobre F/U/m resolvido como 'C': indoorRange.
     Resolvido como 'G': outdoorRange (160px).

   renderRoof():
     F/U/m resolvido como 'C': recebe roof overlay.
     Resolvido como 'G': ignorado (exterior).

50.5 — ESCALABILIDADE

   Para adicionar novo tile especial (ex: 'X'):
     1. Em resolveBaseTile(): adicionar 'X' ao if
        (if (tile !== 'F' && tile !== 'U' && tile !== 'm' && tile !== 'X') return tile;)
     2. Se 'X' precisar de cor dinamica em renderTiles:
        Adicionar case no switch baseado no exemplo de F/U/m.
     3. Nada mais precisa ser modificado.

   Para mudar a logica de resolucao:
     Modificar apenas resolveBaseTile(). O resto consome o resultado.

50.6 — TILES NAO AFETADOS

   P (Player Spawn), M (Monster Spawn), S (Shop), T (Trash):
     Continuam como INTERIOR_COLOR fixo (floor).
     Nao passam por resolucao dinamica.
     Podem ser adicionados futuramente ao escopo se necessario.

   A (Altar), W (Furniture), O (Wall), d (Door):
     Comportamento inalterado.

SECAO 55 — SISTEMA DE HOTBAR RESPONSIVO COM CONTROLE DE TAMANHO E LAYOUT
================================================================================

55.1 — CONCEITO

   O sistema de hotbar do inventario foi refatorado para ser responsivo
   (adapta-se ao tamanho da tela e numero de jogadores) e controlavel
   pelo usuario (tamanho e layout configuraveis no painel de settings).

   Cada hotbar de jogador ocupa uma fracao da largura do container
   #hotbar-hud, calculada como:
     largura% = (100% / numJogadoresVivos) * (hotbarSize / 100)

   Exemplos (hotbarSize=100):
     - 1 jogador: hotbar ocupa 100% do container (overflow; centralizada
       via justify-content:center, ~25% visivel)
     - 2 jogadores: cada hotbar ocupa 50%
     - 3 jogadores: cada hotbar ocupa 33.3%
     - 4 jogadores: cada hotbar ocupa 25%

   O sistema suporta dois modos de layout:
     'horizontal': hotbars lado a lado (flex row), centralizadas, padrao
     'vertical': hotbars empilhadas (flex column), canto inferior esquerdo

55.2 — ESTRUTURA DE DADOS

   NOVAS PROPRIEDADES NA CLASSE Game:

   Game.hotbarSize: Number (inteiro)
     Valor padrao: 100
     Significado: percentual do tamanho base de cada hotbar
     Faixa: 50 a 200 (clampado nos botoes do painel)
     Incremento: ±10 por clique nos botoes [-]/[+]
     Afeta: largura da hotbar, tamanho dos slots, fontes, barra de uso
     Reset: 100 em loadMap() e restart()

   Game.hotbarLayout: String ('horizontal' | 'vertical')
     Valor padrao: 'horizontal'
     Significado: modo de disposicao das hotbars
     'horizontal': flex row, justify-content center, width 100%
     'vertical': flex column, align-items flex-start, max-width 300px
     Alternancia: botao toggle no painel de settings
     Reset: 'horizontal' em loadMap() e restart()

     numPlayers = game.players.filter(p => p.alive).length

     fontSizeSlot  = clamp(28 * hotbarSize / 100, 14, 40) px
     fontSizeName  = clamp(23 * hotbarSize / 100, 10, 30) px
     barWidth      = clamp(50 * hotbarSize / 100, 20, 80) px
     barHeight     = clamp(10 * hotbarSize / 100, 4, 14) px

     slotGap        = 8 px

SECAO 57 — CORRECAO DO SISTEMA DE USO DE ITEM (TECLA R) + BARRA DE PROGRESSO CIRCULAR
================================================================================

57.1 — CONCEITO

   O sistema de uso de item da hotbar (tecla R/use) foi refatorado para
   corrigir um bug onde o slot era ciclado durante o hold, fazendo com que
   o item errado fosse usado. Agora, o sistema distingue claramente entre:

   - TAP (pressionar e soltar em < 0.3 segundos): cicla para o proximo
     slot nao vazio
   - HOLD (segurar por >= 1 segundo): usa o item ATUALMENTE equipado,
     SEM ciclar o slot

   Adicionalmente, a barra de progresso horizontal ciano que aparecia
   ao lado dos slots na hotbar foi removida e substituida por um
   circulo de progresso branco desenhado no Canvas, posicionado
   a direita do personagem.

57.2 — ESTRUTURA DE DADOS (Player.useTapPending)

   Player.useTapPending: Boolean
     Valor padrao: false
     Inicializado no construtor e resetado em loadMap() (via new Player)
     Significado: true = a tecla R foi pressionada e ainda nao se sabe
     se sera um tap ou um hold. Enquanto true, o useTimer conta ate 0.3s.
     Se soltar antes de 0.3s: confirmado como TAP → cicla slot.
     Se passar de 0.3s segurando: confirmado como HOLD → usa item.

57.3 — FLUXO COMPLETO TAP VS HOLD

   ESTADO 1 — REPOUSO (useTapPending = false, useTimer = 0):
     Jogador nao esta pressionando R. Nenhum comportamento ativo.

   ESTADO 2 — KEYDOWN R (keysJustPressed[kb.use] = true):
     Define useTapPending = true, useTimer = 0.
     NAO cicla o slot neste momento.

   ESTADO 3 — DETECCAO (keys[kb.use] = true, useTapPending = true):
     useTimer += dt (conta ate 0.3 segundos).
     Enquanto useTimer < 0.3: ainda em deteccao, nao sabe se e tap ou hold.
     Se useTimer >= 0.3: CONFIRMA HOLD.
       Define useTapPending = false, useTimer = 0.
       A partir daqui, useTimer conta ate 1s para ativar o item.

   ESTADO 4 — USO DO ITEM (keys[kb.use] = true, useTapPending = false,
             inventory[selectedSlot] tem item):
     useTimer += dt (conta ate 1 segundo).
     Se useTimer >= 1: chama game.useItem(player), reseta useTimer = 0.
     O slot NAO muda durante este estado.

   ESTADO 5 — KEYUP R (!keys[kb.use]):
     Se useTapPending = true: foi um TAP.
       Cicla selectedSlot para o proximo slot nao vazio.
       Reseta useTapPending = false, useTimer = 0.
     Se useTapPending = false: foi um HOLD (ou nao havia item).
       Reseta useTapPending = false (ja era false), useTimer = 0.

57.4 — BARRA DE PROGRESSO CIRCULAR (renderUseProgressCircle)

   NOVO METODO na classe Game:
     renderUseProgressCircle(ctx)

   LOGICA:
     - Itera sobre todos os jogadores vivos
     - Se p.useTimer <= 0: pula
     - Calcula posicao: 1 tile (TILE_SIZE = 32px) a direita do centro
       do jogador (p.px + TILE_SIZE, p.py)
     - Converte para coordenadas de tela (subtrai camX/camY)
     - Frustum culling: pula se fora do canvas (margem 50px)
     - Desenha circulo oco com arco de progresso branco

   PARAMETROS DO CIRCULO:
     circleRadius: TILE_SIZE * 0.4 (12.8px)
     lineWidth: circleRadius * 2 * 0.15 (~3.84px)
     startAngle: -Math.PI / 2 (topo, 12 horas)
     progress: p.useTimer / 1 (0 a 1)

   APARENCIA:
     Circulo externo (fundo): rgba(255,255,255,0.2), lineWidth + 2
     Circulo interno (fundo): rgba(255,255,255,0.3), lineWidth
     Arco de progresso: #ffffff (branco puro), lineWidth, lineCap round

SECAO 58 — NOVOS ITENS, RARIDADES E SISTEMA DE CONSUMIVEIS
================================================================================

58.1 — CONCEITO

   O sistema de itens foi expandido de 3 traps para 8 itens com 2 tipos

   que influencia tanto as recompensas de round quanto a geracao de lojas.

   cura) ao jogador que os utiliza.

58.2 — ESTRUTURA DO OBJETO Items

   Campos obrigatorios para todos os itens:
     name: string — nome em ingles
     price: number — preco em coins
     desc: string — descricao curta
     icon: string — caractere exibido no inventario/shop
     color: string — cor CSS hex para o icone
     rarity: string — 'common' | 'rare' | 'super_rare'
     type: string — 'trap' | 'consumable'
     giveOnRoundEnd: boolean — pode ser recompensa de round?

   Campos especificos por tipo:
     type === 'trap': stun (number), trapColor (string), trapRadius (number)
     type === 'consumable': effect (object)
       effect.type: 'speed' | 'invuln' | 'heal'
       effect.multiplier: number (para speed)
       effect.amount: number (para heal)
       effect.duration: number em segundos (para speed, invuln)

58.3 — SISTEMA DE RARIDADES

   Objeto Rarities:
     common:     { name: 'Common', dropChance: 0.65 }
     rare:       { name: 'Rare', dropChance: 0.20 }
     super_rare: { name: 'Super Rare', dropChance: 0.15 }

   Funcao weightedRandomRarity():
     Similar a weightedRandom() para monstros.
     Soma dropChance de todas as raridades (total = 1.0).
     random * totalWeight, subtrai dropChance de cada raridade.
     Retorna a chave da raridade quando r <= 0.

   Funcao getRandomItemByRarity(game):
     - Filtra itens elegiveis (giveOnRoundEnd === true)
     - Sorteia raridade via weightedRandomRarity()
     - Filtra elegiveis pela raridade sorteada
     - Fallback: super_rare -> rare -> common
     - Se ainda vazio, usa todos os elegiveis
     - Retorna key do item aleatorio

58.4 — SISTEMA DE CONSUMIVEIS

   Game.useItem(player):
     Verifica Items[item].type:
     - 'trap': cria trap, remove item (comportamento original)
     - 'consumable': chama applyItemEffect(), remove item

   Game.applyItemEffect(player, itemKey):
     case 'speed':
       Define player.speedItemTimer = effect.duration
       Define player.speedItemMult = effect.multiplier
       Speed final = max(baseSpeed * scoutMult, baseSpeed * itemMult)
     case 'invuln':
       Define player.invulnTimer = max(atual, effect.duration)
       Nao acumula — usa o maior timer
     case 'heal':
       player.hp = Math.min(player.maxHp, player.hp + effect.amount)
       Nao excede maxHp

58.5 — REGRA "MAIOR VALOR VENCE" (SPEED)

   Em Player.update(), o speed e recalculado a cada frame:
     let finalSpeed = this.baseSpeed;
     if (this.abilityActive && this.playerClass === 'scout') finalSpeed *= 1.5;
     if (this.speedItemTimer > 0) {
       this.speedItemTimer -= dt;
       if (this.speedItemTimer <= 0) {
         this.speedItemTimer = 0;
         this.speedItemMult = 1;
       } else {
         finalSpeed = Math.max(finalSpeed, this.baseSpeed * this.speedItemMult);
       }
     }
     this.speed = finalSpeed;

59.3 — SISTEMA DE SPAWN RESPONSIVO

   METODO: Game.findSpawnPosition(baseX, baseY, playerIndex)

   Offsets por jogador:
     P1 (index 0): +0X, +0Y  -> spawn.x
     P2 (index 1): +1X, +0Y  -> spawn.x + 1
     P3 (index 2): -1X, +0Y  -> spawn.x - 1
     P4 (index 3): +2X, +0Y  -> spawn.x + 2

   ALGORITMO:
     1. Calcula tile = baseX + offsetsX[playerIndex]
     2. Verifica isWalkableTile(tx, ty)
     3. Se valido: retorna { x: tx, y: ty }
     4. Se invalido: busca em raio 1 a 5:
        a. Prioriza mesma linha (dy=0): varre dx de -radius a +radius
        b. Tenta linhas acima/abaixo: varre dy=-radius..radius, dx=-radius..radius
        c. Primeiro tile passavel encontrado e retornado
     5. Fallback: retorna o proprio spawn { x: baseX, y: baseY }

   METODO: Game.isWalkableTile(tx, ty)
     Verifica bounds do mapa (tx >= 0 && tx < mapWidth...)
     tile === 'O' || tile === 'W' -> false (parede/movel)
     tile === 'd' e door.solid -> false (porta fechada/animando)
     Senao -> true (passavel: C, G, A, P, M, F, U, S, T, d aberta)

SECAO 60 — SISTEMA DE CONFIGURACAO DE HOTKEYS POR JOGADOR COM DETECCAO DE CONFLITOS
================================================================================

60.1 — CONCEITO

   O sistema de configuracao de hotkeys por jogador permite que cada
   jogador configure suas 7 teclas (Move Up, Move Down, Move Left,
   Move Right, Interact, Ability, Use/Cycle Item) de forma independente,
   tanto ANTES do jogo comecar (na tela de selecao de classes) quanto
   DURANTE a partida (no painel de settings).

   O sistema detecta automaticamente conflitos: quando dois ou mais
   jogadores configuram a mesma tecla, ambos os botoes recebem borda
   vermelha e um tooltip informando quem mais usa aquela tecla. O
   conflito e apenas um AVISO visual — nao bloqueia o rebind.

60.2 — ARQUITETURA DOS DOIS CONTEXTOS

   CONTEXTO A (Tela de Selecao): Antes do jogo comecar, game.players[]
   ainda nao existe. As teclas configuradas sao armazenadas no objeto
   global preGameKeybinds = { playerIndex: { up:'w', ... } }.
   Quando loadMap() cria os players, o construtor Player consulta
   preGameKeybinds[playerIndex] para inicializar this.keybinds.

   CONTEXTO B (Durante Partida): game.players[] ja existe. O painel
   de settings (#settings-panel > #hotkey-config) mostra botoes
   colapsados por jogador. As teclas sao lidas/escritas diretamente
   em game.players[i].keybinds.

   O sistema de rebinding (rebindingPlayer, rebindingAction,
   finalizeRebinding, cancelRebinding) funciona da mesma forma em
   ambos os contextos, com logica condicional para cada caso.

60.3 — ESTRUTURA DE DADOS

   preGameKeybinds: Object
     Chave: playerIndex (0, 1, 2, 3)
     Valor: { up: 'w', down: 's', left: 'a', right: 'd',
              interact: 'e', ability: 'f', use: 'r' }
     Criado: na declaracao global (let preGameKeybinds = {})
     Preenchido: durante rebind na tela de selecao
     Consumido: no construtor Player
     Liberado: em loadMap() (preGameKeybinds = {})

   Game.expandedHotkeyPlayers: Set<number>
     Armazena indices dos jogadores atualmente expandidos no painel
     de settings. Criado no constructor, resetado em loadMap/restart.
     Usado por buildHotkeyConfig para decidir se renderiza
     .player-hotkey-content para cada jogador.

   rebindingPlayer: number | null
   rebindingAction: string | null
     Variaveis globais que rastreiam qual jogador e qual acao estao
     sendo reconfigurados. Usadas por keydown/keyup para interceptar
     a proxima tecla pressionada.

60.4 — FLUXO DE REBIND (AMBOS OS CONTEXTOS)

   1. Usuario clica em um .key-btn
   2. Handler define rebindingPlayer = pi, rebindingAction = act
   3. Remove classe .waiting de todos .key-btn
   4. Adiciona .waiting ao botao clicado, texto = '...'
   5. Usuario pressiona uma tecla no teclado
   6. Keydown listener detecta rebindingPlayer !== null:
      a. e.preventDefault() (impede acao normal da tecla)
      b. Escape: chama cancelRebinding()
      c. Qualquer outra: chama finalizeRebinding(keyName)
   7. finalizeRebinding(keyName):
      a. Se player existe (p = game.players[rebindingPlayer]):
         - Limpa keys[p.keybinds[rebindingAction]] = false
         - Define p.keybinds[rebindingAction] = keyName
         - Reseta rebindingPlayer/rebindingAction = null
         - Chama buildHotkeyConfig(game)
      b. Se player NAO existe (pre-game):
         - Atualiza preGameKeybinds[rebindingPlayer][rebindingAction]
         - Atualiza texto do botao .waiting
         - Remove classe .waiting
         - Reseta rebindingPlayer/rebindingAction
         - Chama checkKeyConflicts()
   8. buildHotkeyConfig() (quando chamada) redesenha o HTML e
      chama checkKeyConflicts() ao final.

60.5 — ALGORITMO DE DETECCAO DE CONFLITOS

   checkKeyConflicts():
     1. Seleciona todos .key-btn:not(.waiting) no documento
     2. Constroi mapa: keyMap[tecla] = [btn1, btn2, ...]
     3. Para cada tecla com 2+ botoes de jogadores diferentes:
        a. Agrupa por data-player
        b. Se 2+ jogadores: marca todos como .conflict
        c. Constroi tooltip: "Conflito: P2 usa W para Move Up"
     4. Para botoes sem conflito: remove .conflict e limpa title

   REGRAS:
     - Mesmo jogador com mesma tecla em acoes diferentes: NAO conflito
     - Jogadores diferentes com mesma tecla: conflito (ambos marcados)
     - 3+ jogadores: todos os botoes conflitantes marcados
     - Conflito NAO bloqueia rebind — apenas avisa
